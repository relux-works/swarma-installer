# Linux install plan for colony1, v0

Status: design proposal, round 4. Written for the repository `relux-works/swarma-installer`. Nothing here is implemented, and this document installs nothing. Identifiers: `D-..` rows of `01-book-mapping.md`, `OD-..` rows of `05-open-decisions.md`, `V-..` and `U-..` rows of `03-verifier-contract.md`.

The books are the target. colony1 runs a TEST PROFILE: the closed list of NINE deviations in the first table. Every row of files 3 and 4 that departs from a book points either to one of the nine (a test-profile departure, colony1 only) or to the ruling or owner decision that made that departure for every machine (listed row by row in the table "Departures that are not test-profile deviations" below); a departure that points to neither is a defect, and the one departure that is still open (the authentication count, OD-23) has its dependent rows marked NOT RUNNABLE on that point. The plan covers Linux only. The machine itself is one fresh Debian VM; three parts of the installation live outside it and are prerequisites (table "Prerequisites"). The commands are `swarma install` and `swarma uninstall`.

**The plan cannot run today.** Every row marked `MISSING` or `NOT RUNNABLE` names what does not exist and who owns it; the table "MISSING preconditions" collects them.

## The one machine identity

One value names the machine everywhere: in the test-profile gate, in the key service's signed static statement, and later in the machine attestation. No second machine identity is defined.

| Property | Definition |
| --- | --- |
| Source | The host's `/etc/machine-id` file, read as EXACT bytes with nothing trimmed (the trailing LF is included), as a root-owned, regular, single-link file through a protected reader, bounded at 4096 bytes. |
| Value | Lowercase hex SHA-256 of those exact bytes, 64 characters. An all-zero digest refuses. This is the value the key service's static statement binds as `host.machine_id_sha256`; the statement's `host.label` is audit-only and authenticates nothing. |
| Reference value (outside the machine) | The owner holds the machine identity OFF the machine: it is the digest captured from the clean VM after its first boot, before the clean copy of it is taken (P-03). That held value, typed in the administrator session, is the only reference the gate ever compares against. No value read from the machine being checked is ever its own reference. |
| Where the plan uses it | P-03 (the owner holds it off the machine, captured once as above), S-02 (reads the owner-held value typed in the administrator session and compares it with root's computation; on a mismatch it refuses and writes nothing), G-01 (the gate, against the S-02 record of the owner-held value), P-07 (the statement binds the owner-held value, so S-17 is an independent second check), S-17 (root compares statement, record and machine). The key service's own refusal for a mismatch is its `STATIC_GATE_HOST`. |

## How to read the tables

- **Precondition** is what must already be proved. `MISSING (owner: X)` means the step needs something X does not offer today; the step is `NOT RUNNABLE` until X delivers it. This plan does not design X.
- **Account** is the OS account whose process performs the action: `root`; `admin` (the person at the administrator session: on colony1 the infrastructure lane runs the root steps and the owner approves the digests); `owner account` (the unprivileged account that holds Curator); `operator` (the operator account, entered by TP-3); `service: <role>`; `agent: <role>`.
- **On failure** is what happens when the step proves that it failed: stop, report the step and the code, leave the machine in the last confirmed state. The plan never undoes earlier rows by itself, with one exception that has its own row: S-35 stops agents that S-34 started.
- **On UNKNOWN, and a second run** is what happens when the step cannot prove whether its effect happened, and what a later run of the installer does at this step. "Stops for ever" is not a row: every such cell ends in an act, in a refusal with a code, or in a named operator action. The same discipline applies to a reboot: table "Boot" (B-01) rows what a reboot does to every state this plan can be in.
- Service accounts are named by role. Where a source gives a public account name it is the name of the install book's table "Parts and their accounts".

## The step record: one record pair per effect

A table row of the plan is not a unit of recovery. Every externally visible EFFECT (each account, each confirmation, each pin, each registration, each binding, each start, each file) has its own intent and result, with its own replay identity and read-back. A step is confirmed only when every effect its row names has a result of `new state`. A partial step is never recorded as one `other`: three created, one rolled back and six not attempted is ten effect records in three states, and the run resumes at the first effect without `new state`.

| Property | Definition |
| --- | --- |
| Who writes it | Root, for every effect except those of S-05a and S-08b, which act under the owner's account. For an effect made by a service or by the operator (for example S-28), root writes the intent before it asks for or waits for the act, and the result after root or the observer account read the evidence. S-01 is outside this mechanism (it runs before the records directory exists); its own evidence is stated in its row. S-08a (root's handoff copy) is a root step with records; only S-08b is an owner-account step. |
| Where | `/var/lib/swarma-install/records/`, root:root 0700. It is outside the platform root, so removal never deletes it (R-11, R-12). |
| Owner and mode of a record | root:root 0600, one file per record, never rewritten. |
| When in the effect | Intent: after the preconditions are proved and before the first change. Result: after the evidence was read. An effect whose intent cannot be written does not act. |
| How it is written | By G-10: temporary file in the same directory, flush, rename, directory flush. A record is wholly absent or complete. |
| File name | `<sequence>-<step>-<effect>-intent`, `<sequence>-<step>-<effect>-result`, and `<sequence>-<step>-<effect>-binding` for the two-phase form below; `<sequence>` is a decimal counter that only grows. The byte encoding of the content is MISSING (owner: the installer specification); its members are fixed by the next rows. |
| Members of an intent | Step id; effect id; run id; the approved plan digest; the set digest; the exact planned effect; the OBJECTS this effect changes (for G-03b); every request identity the effect will use at a service (table "Replay identity"); the observed BEFORE-state of every object the effect may change (absent, or owner, mode, type and digest). |
| Members of a result | Step id; effect id; run id; one of `new state`, `old state`, `other`; the facts read, each with the account that read it. |
| Records of the two owner-account steps | Written by that account under its own state directory, mode 0700. They are notes for that account. Root never reads them (G-05). No later root precondition names S-08b as observed; what later steps use under agent accounts is root's own copy (S-09). |

Where a service chooses an identity that the intent cannot contain beforehand (it mints and stores it), the record is TWO-PHASE: (1) the intent fixes the subject the identity is bound to (the stable role name, the generation, the exact request bytes); (2) after the service answers, and BEFORE any effect uses the identity, root writes a binding record that binds subject to identity from the read-back; (3) only then may an effect use it. An identity must be derivable from the fixed subject by a formula stated in the replay table, or bound this way; an effect that can be neither is marked MISSING against its service and does not run. A resumed run reads the binding record and the service's state and compares; it never asks for a second identity for one subject.

How every unknown-outcome rule follows from the record, per effect:

| What the run finds for an effect | State | What the run does |
| --- | --- | --- |
| No intent, and no temporary file for this effect | not started | Proves the preconditions, writes the intent, acts. |
| A temporary file for this effect, and a surviving final intent | a write was torn; the effect is pending, never not started | Under the lock (G-02): treats the effect as pending, observes it as for "intent, no result" against the surviving intent, then removes the temporary file. |
| A temporary INTENT file for this effect, and NO final intent | not started (proved, not believed) | An effect whose intent cannot be written does not act (property "When in the effect"), so a torn intent with no final intent proves the effect never acted. Under the lock (G-02) the run removes the temporary file and treats the effect as not started: proves the preconditions, writes the intent, acts. It does not stop, and it does not guess beyond that proof: where the temporary file's own step and effect cannot be established from its name, it is not this case and the run stops for the admin (`record_unreadable`). |
| Intent, no result | pending | Observes the facts the row names, using the before-state and request identities of the intent; writes the result; continues only on `new state`. |
| Result `new state` | confirmed | Re-reads the evidence (G-03b, against the last writer). Equal: continues. Different: stops with `step_drift`. |
| Result `old state` | the effect did not happen | Starts the effect again with a new intent, unless the row forbids a repeat. |
| Result `other`, or a final record that cannot be read | unknown | Stops for the admin (`record_unreadable` for the second case; that code is kept for unreadable FINAL records, never for a torn intent covered above). |

## Facts a re-run reads, and when each becomes stable

A re-run compares the machine only with facts that are stable at the step being resumed. Facts the install itself changes later are compared with their last confirmed writer (G-03b), never with the pre-install survey. ## Start order in one line

At boot: the static range deny loaded and probed, before anything else of the installation (B-01). Then key service, credential broker, credential gateway, chain gateway, dispatcher, bridge; then the proof gate; then the hold is released per role and the three agents start: orchestrator, worker, reviewer. After a reboot the same line holds with the description held again and the proof gate run again in that boot before any release. The user manager and the launcher are not units: each runs as root for one operation and exits.

## Where the model credential is, in one paragraph

The credential is enrolled at the BROKER by an operator act of the owner, who logs in himself. The broker is the only holder of every enrolled credential and its only refresher. The gateway holds leased material only, under a service lease, in its own account. An agent account holds a placeholder bound to one generation, one run and one account, which works only on that generation's own gateway listener. The installer never sees the value. S-21 proves exactly one lease, and S-33 proves, before any agent starts, that no agent account can read the broker's store or the gateway's state, next to a positive control from each holder, and that a call after its binding's revocation refuses (line (k), black-box). On colony1 the broker and the gateway reach the provider directly (TP-7); the plan claims no enforced service egress.

## Where messages go, in one paragraph

An agent signs its exact outgoing bytes through the key service and hands the complete signed envelope to the bridge's local submit endpoint. The bridge runs under the shared messages account and holds the only carrier credential. No agent account holds a carrier credential; S-29 places none and S-33 line (e) proves it before the first start. One OS account is one message author.

## What this plan does not cover

- Update, rollback and the transaction state the install book assigns to an installer specification.
- macOS (one required row is named in the table above) and a second host.
- The keeper (TP-4), the product session host (TP-5), the egress proxy (TP-7), resource ceilings (TP-8) and signed machine evidence (TP-9). The repository-actions service, the updater, the machine's enrolment record in the machine registry and the owner's channel are outside the first set by ruling OD-5, not deviations of this plan.
- What a reboot does beyond B-01: after a reboot the description is held again and the deny is loaded and probed first (B-01, with its read-backs), and nothing starts the three agents until a person runs S-33 and S-34 in that boot. The installed result is therefore long-lived until process death or reboot, not beyond. Whether the host may re-raise the team automatically once that boot's gate passes, without the operator, is the owner's open decision OD-11 (file 5, narrowed); the plan claims nothing about a reboot that B-01 does not row.
- Opening admission, issuing grants and signing anything. Those belong to the dispatcher, the operator and the key service.
- Fault-injection tests of these rows. The install book requires, for every refusal and invariant, a negative check with a positive control; this package gives the rows such a test must cover and runs none. That is the implementation unit's acceptance gate.
