# Verifier contract v0

Status: design proposal, round 4. Written for the repository `relux-works/swarma-installer`. Nothing here is implemented. Identifiers: `D-..` rows of `01-book-mapping.md`, `OD-..` rows of `05-open-decisions.md`, `S-..`, `R-..`, `G-..` and `TP-..` rows of `04-install-plan-colony1.md`.

The verifier decides whether one release set may be installed. Its trust inputs reach root only through the administrator session: the **approved digest** (the set digest the owner approved in person, TP-1) and, on the test profile, the approved digest of the second-build comparison record (TP-6). It never unpacks an archive, never executes a byte of an artifact and never fetches from a network: its byte source is a directory of files.

The rule this contract exists for: **a privileged step acts only on what root itself verified on root's own protected copy.** The same checks can run under the owner's unprivileged account, but that run is advice. Its output is never an input of a root step.

## Modes

No mode skips a blocking check silently. Where a mode does not run a check, this table says so and says what that mode can therefore never return.

| Mode | Who runs it | Byte source | Checks | Does NOT run, and can therefore never return | Closed result set | What its result may be used for |
| --- | --- | --- | --- | --- | --- | --- |
| `shape` | anyone; the test harness | one manifest file | V-04 to V-12, then V-13 and V-14 under a named host | V-01 to V-03 and V-15 to V-21. It can never return `verified` or `advisory_ok`, and `shape_ok` says nothing about approval, artifacts or builds. | `shape_ok` or a refusal code of V-04 to V-14 | Vectors and tooling only. |
| `advisory` | the owner's unprivileged account | any directory the account can read; the comparison record is the account's own copy there (never root's protected copy) | V-01 to V-18 and V-20, with the approved digests typed by the person | V-19 (the first-install binding) and V-21 (no record is written). It can never return `verified`, and `advisory_ok` says nothing about the first-install binding. Without a comparison record it ends at V-20 with `second_build_missing`; it never ends early with success. | `advisory_ok` or a refusal code | A preview for a person. No root step reads it (plan row G-05). |
| `authoritative` | root, in the administrator session (plan S-04) | the protected directory only (table "The protected directory" in file 4); the comparison record is root's protected copy there | V-01 to V-21, every blocking check | nothing | `verified` or a refusal code | The only result a privileged step may rely on. |

## The second-build comparison record (test profile, TP-6)

On the test profile the comparison of artifact digests with a second, independent build replaces the provenance check (ruling OD-15; deviation TP-6). The offline-checkable provenance record stays a duty of the release standard for the product; v0 defines no product profile, so no v0 run can select it.

| Property | Definition |
| --- | --- |
| Who produces it | The two reads of each release, in the release process, before the set manifest is assembled: each read builds independently and reports the digest it built, per artifact. The release operator assembles one record per release set from their comparisons. The installer produces nothing of it. The producing reads are carried in the record as audit-only members (below); no identity in it gives it weight — only the owner-approved digest of the record does. |
| What it lists (members fixed here; byte encoding MISSING, owner: the installer specification) | The set digest it belongs to. The producing reads, as audit-only members that authenticate nothing. For every artifact the manifest lists: the product, the artifact `sha256` from the manifest, the digest the second independent build produced, and — where the encoding carries one — whether the two are equal. That equality member is audit-only: V-20 compares the two digests itself and never acts on the flag (see V-20). No other member gives it weight. |
| How root reads it | As a root-owned copy in the protected directory (`approval/second-build`, root:root 0600), written by root in plan step S-03 from the file the admin names. It is governed by its own input rules (V-20, steps 1 to 3), modelled on V-02 and V-03 for the manifest: opened per path component without following links, checked on one held descriptor (authoritative mode: root-owned, regular, single link), read at most cap + 1 bytes (cap in the limits table), and its buffer hashed and compared with the approved comparison-record digest of V-01 **before any byte of it is parsed**. A record the owner's unprivileged account can rewrite is never read in authoritative mode. In advisory mode the same order applies to the account's own copy, with the approved digests typed by the person and without the ownership clause. |
| Which check consumes it | V-20, in advisory and authoritative mode. Shape mode does not run V-20 (see the modes table). |
| Size bound | The record is at most 65536 bytes (limits table). S-03 copies at most cap + 1 bytes of it and refuses a longer source (plan S-03); V-20 refuses a longer copy. A set whose record needs more is refused, not truncated. The value is provisional with the rest of the limits table (ruling OD-17). |

## The contract

Checks run in the order of the table. The first failing check ends the run with its code. "Written before it" names everything the verifier has written when the check starts. The verifier holds one open descriptor per file and does every size, type, hash and parse operation through that descriptor and one in-memory buffer; it never re-opens a path it already checked.

## Unpack contract

Unpacking is not part of the verifier. It is listed here because it is the next consumer of the verifier's result. The rules apply to every `tar.gz` artifact, whoever unpacks it: root for `platform-root` products (plan S-09) and the owner's account for `owner-account` products (plan S-08b). The first-install `deb` is installed by the operating system's package installer (plan S-01) and is outside these rules; what bounds it there is stated in S-01.

Rules are tested per entry in the order of the table. "Name" always means the EFFECTIVE entry name after pax `path` records and GNU long-name records are applied; a stream whose name records do not resolve to one effective name per entry refuses under the first name rule it breaks. The first failing rule refuses the WHOLE archive: the staging directory of that attempt is removed, and nothing of the archive appears under a final name. Every case has a row in `vectors/unpack-cases.json`.

| Rule | What is required | Refusal code | Refused example | Valid neighbour |
| --- | --- | --- | --- | --- |
| U-01 the copy is the verified copy | Immediately before unpacking, the unpacker hashes the exact file it will read, through the descriptor it will read from, and compares with the `sha256` of the verification record (root) or of the root-owned handoff copy of the manifest (owner account). | `unpack_copy_changed` | a copy with one byte changed after verification | the unmodified copy |
| U-02 closed format list | The file is one gzip member holding one POSIX tar stream. No other container or compression is accepted. | `unpack_format_unknown` | a zip file under a `tar.gz` artifact | a gzip-compressed tar |
| U-03 no absolute path | No effective entry name starts with `/`. | `unpack_path_absolute` | `/etc/example` | `bin/example-manager` |
| U-04 no parent reference | No effective entry name has a component `..`. | `unpack_path_traversal` | `../../.profile` | `bin/example-manager` |
| U-05 plain paths | Every component of the effective name is 1 or more bytes of `0x20`-`0x7e` without `/` and `\`, and is not `.`. One trailing `/` on a DIRECTORY entry is allowed and stripped before the component test; more than one is an empty component. A path has at most 255 bytes and 16 components. | `unpack_path_invalid` | `bin//x` | `bin/x` |
| U-06 no links | No symbolic link entry and no hard link entry, wherever they point. | `unpack_link_refused` | a symbolic link `bin/x` | a regular file `bin/x` |
| U-07 regular files and directories only | No device, FIFO, socket or any other entry type. | `unpack_special_file` | a character device entry | a regular file |
| U-08 no special mode bits | No entry carries setuid, setgid or sticky. The unpacker sets owner and mode itself: directories 0755, files 0644, or 0755 when the entry has an owner execute bit. Owner and group come from the unpacker (root:root for root, the account itself otherwise), never from the archive. | `unpack_mode_refused` | a setuid file entry | the same file without the bit |
| U-09 no extra metadata | No extended attribute, no `security.capability`, no access control list record in any header. | `unpack_metadata_refused` | an entry with `security.capability` | the same entry without it |
| U-10 one entry per destination | No two entries resolve to one destination path by effective name, and no entry lies under a path that an earlier entry made a file. An existing destination is never overwritten. | `unpack_entry_duplicate` | two entries `bin/example-manager` | one entry |

| U-12 entry count | At most 4096 entries. | `unpack_entry_count_exceeded` | 4097 entries | 4096 entries |
| U-13 nothing after the archive | No second gzip member and no byte after the end-of-archive marker. | `unpack_trailing_data` | a second gzip member | a single member |
| U-14 placement | After unpacking, every file the placement table of the plan names for this product exists as a regular file → else `placement_missing`. How the unpacker writes: into a NEW, empty staging directory that it created exclusively inside the destination's parent, with every open relative to that directory's descriptor and resolved beneath it without following any link. Only after the last entry passed and U-14 holds, the staging directory is flushed and renamed to its final name. An interrupted unpack leaves a staging directory and no final name.

## Why the order holds

- V-01 to V-15 read only the approval record and the manifest and write nothing. The manifest is hashed and compared with the approved digest (V-03) before one byte of it is parsed. The comparison record is read under the same discipline inside V-20: bounded, on one held descriptor, hashed and compared with its approved digest before one byte of it is parsed, and its equality is then computed, never read from a flag.
- An artifact is opened by its digest, read once through one descriptor, bounded by its declared size, and hashed. It is never parsed and never executed by the verifier.
- The verifier has no unpack step. The FIRST unpack of the whole plan is S-08b or S-09, both after S-04 returned `verified` over root's protected copies, and each unpacker re-hashes its own copy immediately before it reads it (U-01). No step before S-04 unpacks or executes any byte of the set. The one exception is by design of the install book: the first-install package is installed in S-01 on the owner's comparison of its digest, before any installer code exists on the machine.
- A result of the advisory mode is never an input: the authoritative run reads nothing the owner's unprivileged account can write (plan row G-05 and the protected directory table).

## The trust root of v0 and its target

The trust root of v0 on the test machine is the owner's in-person approval of exact digests: the set digest and the comparison-record digest (TP-1, TP-6). Service repositories publish pre-releases with checksum files and provenance; a signature on them made with a key that automated sessions can use proves nothing about origin, and the verifier gives it no weight. The two reads of each release compare the built artifact digests with a second, independent build before the set manifest is assembled; the record of that comparison is what V-20 checks, and the owner's approval rests on it.

The verifier never learns an approved digest from the network, from a manifest, from a repository, from an environment variable or from an argument. With no approved digest it refuses with `approved_digest_absent`. It has no flag that skips a check.

The target, decided by the owner: the product's trust root is the owner's OFFLINE publisher key, with its FINGERPRINT in the install command. The install book describes a different final scheme (an update root, offline threshold keys, part signatures, a transparency log); the book text must follow the owner's decision. Until the offline key exists, no release is presented as signed in the product sense.

## Unknown outcome

- The verifier writes only the verification record, last, on the first run, by temporary file, flush, rename and directory flush. On a resumed run it writes nothing: V-21 compares the record it would write with the stored one instead of rewriting it, so no write of a resumed run is left without a covering record. Without a complete record whose set digest equals the approved digest, the set is not verified, whatever the files look like.
- A re-run never trusts an existing verification record alone: once S-04 is confirmed, plan row G-03 makes every run repeat the FULL authoritative check (V-01 to V-21, the first-install binding and the build check included) over the protected copies before the first unfinished step. Before S-04 is confirmed, a re-run creates the inputs first (plan S-01 to S-04); it does not demand them.
- `io_error` means the verifier could not tell whether a read or a write succeeded. It is a refusal; it is never retried inside the same run.
- An advisory run leaves nothing behind. It has no quarantine directory.

## Limits of v0 that the reader should know

- There is no freshness or rollback check. The owner can approve an old set; nothing in the machine objects.
- The approval is exactly as good as the path by which the digests reach the administrator session. On the test machine the infrastructure lane runs the root steps and the owner approves the digests (plan, prerequisites); the approval record is root-owned, so the owner can re-read afterwards exactly which digests were used.
- The verifier trusts the host's SHA-256 implementation and the operating system's report of the host platform.
- A passed verification says the bytes are the bytes the owner approved and that a second independent build produced the same digests. It says nothing about what the bytes do.
